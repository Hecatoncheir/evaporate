# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Evaporate — десктопный лончер игр на Flutter (macOS / Linux / Windows): библиотека,
встроенный BitTorrent-клиент и перенос сохранений между устройствами. Каталога
контента в приложении нет — источник каждой игры задаёт пользователь.

## Команды

```bash
flutter pub get   # обязателен первым: он же генерирует lib/l10n/app_localizations*.dart
flutter test
flutter test test/services/saves/save_manager_test.dart      # один файл
flutter test --plain-name 'метка правила'     # один тест или группа по имени
flutter run -d macos
```

Сгенерированные `lib/l10n/app_localizations*.dart` не в репозитории, и
**неявный `pub get` внутри `flutter test` их не создаёт** — на свежем клоне без
явного `flutter pub get` (или `flutter gen-l10n`) всё, что импортирует
локализацию, не соберётся. То же после правки `.arb`.

Перед отправкой правки — ровно то, что гоняет CI (`.github/workflows/ci.yml`),
одной командой:

```bash
dart tool/gate.dart
```

Внутри формат, анализатор, `bloc lint`, сверка регистраторов плагинов, тесты
в случайном порядке с покрытием и порог покрытия; идут все шаги, итог — кодом
возврата. Перечень держался памятью в три команды и отстал от CI на четыре
шага, поэтому теперь он в одном месте, а `gate_test.dart` сверяет его с
`ci.yml`: новый шаг CI без строчки в воротах роняет прогон. `bloc lint`
идёт из `dev_dependencies` (`dart run bloc_tools:bloc lint lib`) — ставить
его отдельно не нужно.
Ворота же — хуком перед отправкой, по желанию:
`git config core.hooksPath .githooks`. Разошлась версия Flutter с
`FLUTTER_VERSION` — ворота предупредят: форматтер между патчами расходился.

`tool` в списке не для красоты: `tool/check_coverage.dart` импортируется из
`coverage_report_test.dart`, а `tool/changelog_notes.dart` запускается на
теге — это обычный код проекта, и формат с него спрашивают так же.
Запускают скрипты голой Dart VM (`dart tool/…`), где Flutter нет, и ни один
не должен дотягиваться до него — ни сам, ни через `lib`: так
`tool/rehearse_update.dart` через распаковку обновления перестал
собираться, и 0.40.1 не вышла. Тесты этого не видят, они идут под
Flutter, — сторожит `tool_imports_test.dart`.

**Анализатор считает провалом и подсказки (info), не только ошибки.** Смотрите
весь его вывод, а не отфильтрованный по слову `error`.

Прочее:

```bash
python3 tool/make_icon.py        # перерисовать иконки (png, .ico, набор для macOS)
python3 tool/fetch_manifest.py   # положить настоящий манифест Ludusavi в third_party/
flutter build macos --release    # linux / windows аналогично
```

Тесты не требуют ни сети, ни геймпада, ни собранного приложения. Часть
пропускается по платформе (реестр — только на Windows, `.app` — только на
macOS), это норма: **прогон идёт на всех трёх системах**, поэтому пропущенное
здесь выполняется там. `ludusavi_manifest_bench_test.dart` пропускается без
скачанного манифеста.

CI: `analyze` (формат и анализатор, ubuntu), `test` — матрица из ubuntu,
macOS и Windows с `fail-fast: false`, — и `coverage`, который сливает их
покрытие.

**Покрытие — порог, а не отчёт.** Снимается на каждой из трёх систем:
тесты там пропускают разное, и тест, который идёт только на Windows или
macOS, при покрытии с одной ubuntu можно было удалить незаметно. Задание
`coverage` сливает три отчёта (строка выполнена, если хоть одной
системой), кладёт итог в сводку прогона и в артефакт `coverage-<sha>`, а
`tool/check_coverage.dart --all-systems` при недоборе валит прогон: 82% на весь код без генерации, 82% на
`lib/core` + `lib/models` + `lib/services`, 90% на `save_manager.dart` с
`restore_transaction.dart` (оба порога считаются по этим двум файлам, и
разбор менеджера на части их не сдвинул). **Файл, не выполнявшийся ни разу, в отчёт не
попадает вовсе** — и процент не снижает, а повышает, — поэтому такие
названы поимённо (`_reportedNowhere`): новый безмолвный файл валит прогон. **А тонкий — тоже:**
общий процент прячет файлы с нулём, поэтому у каждого файла ниже 50% своё
число в `thinFiles` — новый такой роняет прогон, названный не опускается
ниже своего, доросший уходит из списка. Числа — по слитому отчёту, на
три пункта ниже достигнутого; по отчёту одной системы (локально) список
только показывается: пропущенные там тесты делают файлы тоньше, а флаг
`--all-systems` сам проверяет, что отчётов три. **Числа держат на два-три пункта ниже
достигнутого и поднимают следом за ним**: вровень придвинутый порог валит
прогон на любой мелочи и кончается тем, что его опускают, а отставший
вдвое не ловит ничего — можно выкинуть треть тестов, и прогон смолчит.
Локально порог проверяют ворота; отдельно:

```bash
flutter test --coverage && dart tool/check_coverage.dart
```

**Ещё один шаг `analyze` — `git diff --exit-code linux windows macos`.**
Регистраторы плагинов генерирует `pub get`, а лежат они в репозитории: обновив
зависимости, их коммитят вместе с правкой. Расхождение молчит — файл
компилируется, просто не регистрирует плагин, — и однажды так от релиза к
релизу не работало перетаскивание в окно на Linux и Windows.

`site/` и `design/prototype-v2|v3` в сборку приложения не входят: их
выкладывает на GitHub Pages отдельный `.github/workflows/pages.yml`, и только
при изменении этих путей.

Описание релиза не пишется отдельно: задача выпуска достаёт раздел версии из
`CHANGELOG.md` через `tool/changelog_notes.dart` и кладёт его в релиз. Релиз
заводится черновиком, публикуется после выкладки архивов и остаётся черновиком,
если раздела для версии нет. На теге раздел проверяется до сборок, а
`changelog_notes_test.dart` сторожит верхний раздел файла — тот, который
выпустят следующим.

Версия Flutter зафиксирована в `env.FLUTTER_VERSION` (3.47.4, Dart 3.13.3).
Сборки трёх платформ идут на теге `v*`, ручным `workflow_dispatch` и раз в
неделю по расписанию — тесты не компилируют ни раннеры плагинов, ни CMake,
ни шейдер, ни мастер установки, и без расписания сломанная сборка
обнаруживалась бы в день выпуска;
на теге же архивы прикладываются к релизу и берут артефакты по маске
`evaporate-*` — иначе к релизу уехал бы и отчёт о покрытии. Каждая сборка
выпускает установщик и архив: установщик человеку, архив приложению для
обновления по нажатию (`windows/installer.iss`, `tool/package_macos.sh`,
`tool/package_linux.sh`, `tool/package_run.sh`, `tool/package_tarball.sh`).

**Собранное запускается до выкладки** — `evaporate --smoke`
(`SmokeRun`, `lib/services/system/smoke_run.dart`): приложение поднимается
целиком во временном доме (`AppPaths.init(home:)` — ни данных человека, ни
чужого замка экземпляра), доживает до первого кадра, пишет файл
`JsonStore` с правами, проходит штатное завершение и отвечает кодом
выхода. Прежде собранное не запускалось ни разу: тесты не видят ни
регистрации плагинов, ни бандла. На macOS и Linux запускается не папка
сборки, а архив релиза, распакованный нашим `UpdateUnpack`
(`tool/rehearse_update.dart`) — то, что разложит обновление у человека;
на macOS распакованное сперва проходит `codesign --verify --deep`:
потерянный внутри фреймворка симлинк видно только так. Linux — под
`xvfb-run` и своей шиной DBus. Что остаётся рукам — чек-лист перед тегом
в `CONTRIBUTING.md`.

**Выпуск версии — раздел в `CHANGELOG.md` со ссылкой на тег внизу файла, и
сам тег.** Больше её нигде нет: номер задаёт тег, а CI передаёт его в сборку
(`--build-name` и `--dart-define=EVAPORATE_VERSION`). В `pubspec.yaml` и в
`AppVersion.dev` стоят нули — это «сборка не из релиза». Порядок выпуска и две
грабли, на которые уже наступали (тег ставят на зелёный `main`; `push.followTags`
утаскивает локальные теги), записаны в `CONTRIBUTING.md` — здесь их не дублируем.

## Обновление по нажатию

`update_check` / `update_download` / `update_install` / `update_installer` в
`lib/services/system/`. Файл в релизе ищется **по хвосту имени**
(`Release.updateSuffix`), и системы тут расходятся: macOS и Linux берут архив
(`-macos.zip`, `-linux-x64.tar.gz`) и заменяют папку, **Windows берёт установщик**
(`-windows-setup.exe`) и запускает его отсоединённым процессом — так между
приложением и заменой не остаётся ненадёжного PowerShell-помощника. Скачанное
проверяется по порядку: размер, потом sha256 из `SHA256SUMS`, и только потом
распаковка. Канал защищён TLS, но оборванная загрузка выглядит целым файлом, а
разворачивают её поверх установки. Подписи под суммами нет намеренно: её
сделали и убрали — ключи для одного проекта сочли лишними
(`docs/decisions/0008`); не предлагайте её снова без нового довода.

Замену на macOS и Linux делает POSIX-помощник, и порядок его шагов —
возможность откатиться: дождаться, пока процесс исчезнет; **отодвинуть**
текущую папку, а не удалить; поставить новую; запустить; и только теперь убрать
отодвинутое. Сорвись замена на середине, прежняя установка ещё лежит рядом.
Помощник работает, когда приложения уже нет, поэтому пишет в свой журнал, а
приложение забирает его при следующем запуске (`collectLog`) — иначе о
неудавшейся замене не узнал бы никто: окно закрылось, не открылось, и ни следа
почему.

**Обновить можно не всякую копию, и молчать об этом нельзя.** На Windows —
только поставленную Inno Setup (проверка по `unins000.exe` рядом): portable-zip
не превращают в установленную копию без спроса. На остальных системах решает
пробная запись в папку приложения: положенное пакетным менеджером (`.deb`
ложится в `/opt`) обновлять должен он же. Отказ приходит сообщением
«обновите тем способом, каким ставили», а не тишиной.

**Заменяется только своя папка.** Замена удаляет папку приложения, а ею
считается та, где лежит исполняемый файл: архив Linux, паковавшийся
россыпью и распакованный прямо в «Загрузки», делал папкой приложения сами
«Загрузки», и обновление уносило их целиком. Поэтому на Linux нужна ещё
метка сборки — `.evaporate-install` (`InstallLayout.marker`) — и ни одной
записи верхнего уровня сверх `evaporate`, `lib`, `data` и её самой. Метку
кладут архив (`tool/package_tarball.sh`, с корневой папкой `evaporate/`) и
`.run`; пакет `.deb` её не несёт — его файлы принадлежат dpkg. Помощник
перепроверяет своё перед каждым `mv` и `rm -rf` сам: он последний рубеж и
не верит тому, кто его собрал. Хвост архива сменён с `-linux.tar.gz`
нарочно: замену выполняет помощник *установленной* сборки, и прежний, не
знавший проверки, не должен найти, что скачивать. Прежний хвост в релиз
не кладут — `release_artifacts_test` это сторожит.

Имена файлов связывают CI и приложение, и разойтись они могут молча, поэтому
`release_artifacts_test.dart` читает сам `ci.yml` и `windows/installer.iss`.

## Язык

Комментарии, документация, `CHANGELOG` и сообщения коммитов — по-русски.
Комментарий объясняет **почему**, а не что; хороший отвечает на «почему не
проще?». Тест называется утверждением о поведении («свежий прогресс не
затирается старым пакетом»), а не именем метода.

Все видимые строки живут в `lib/l10n/app_ru.arb` (исходник) и `app_en.arb`
(обязателен). Тесты-стражи в `test/guards/localization_test.dart` сверяют наборы
ключей, подстановки и обходят `lib/ui` в поисках кириллицы в строковых
литералах — при срабатывании строку выносят в ARB, а не глушат проверку.
Там же сторожатся исключения, текст которых человек читает как есть
(`UpdateException`, `SaveException` и соседи — список поимённо): русский
литерал в них не пишут. Где языка нет — изолят, статика разбора, —
исключение несёт причину, а слова к ней подбирает тот, у кого язык есть
(`UpdateException.describe`).

Исключение помечено в коде: журнальная подпись модели (`logLabel`) и
функции в `lib/core/format.dart` остаются русскими намеренно — они идут в
журналы. Интерфейсу `.logLabel` запрещён стражем: так в английской
локали и показалось «Source: Локальная папка». Переводимые подписи для показа собраны в `lib/ui/labels.dart`, потому
что у моделей и слоя ввода нет `BuildContext`. Подпись, нужная ещё и блоку
(состояние движка в `Notice`), лежит в `lib/l10n/labels.dart`: блок не
импортирует `lib/ui`.

**Числа, даты и размеры для показа — по языку**: `bytesLabel`,
`dateTimeLabel` и `countLabel` в `lib/l10n/labels.dart` («1,5 ГБ» и «1.5 GB»,
«22.09.2026» и «9/22/2026»). `formatBytes` и `formatDateTime` из
`lib/core/format.dart` — для журналов и для того, что хранится в снимке и
уезжает на другие устройства: `DateFormat` языка требует данных, которые
загружает интерфейс, и в сервисе без него он падает.

**`SavePathRule.defaultLabel` («Сохранения») не переводится.** По метке правила
сопоставляются между устройствами: переведись она, снимок с русской машины
перестал бы сходиться с правилом на английской. Хранится как есть, переводится
только показ (`ruleLabelText`).

## Состояние: по умолчанию Bloc

Блоков уровня приложения семь — их раздаёт `main.dart`: `SettingsBloc`,
`LibraryBloc`, `SavesBloc`, `DownloadsBloc`, `NavigationBloc`, `UpdateBloc`,
`DownloadHistoryBloc`. Остальные в `lib/bloc` живут со своим экраном или
диалогом. Каждый блок — папка `lib/bloc/<feature>/` из событий, состояния
и обработчиков, связанных через `part`. Состояния иммутабельны (`Equatable`);
у `SettingsBloc` файлов два, потому что состояние у него — сам `AppSettings`.

**Новое состояние — блок с событиями.** Cubit допустим, только если верно
всё сразу: состояние живёт не дольше одного виджета или диалога; нет
асинхронной работы и внешних источников; переходы — простые присваивания
(переключатель, выбранная вкладка). Доводы за блок:

- **журнал причин** — у события есть имя, и в журнал уходит «что
  случилось» (в выпускной сборке — имя события, в отладке ещё и «что
  изменилось»); для приложения, где журнал — единственный
  способ узнать, что произошло у человека, это главное;
- **трансформеры** — очередь, задержка набора, «второе нажатие не в счёт» —
  свойства события, их не сделать методом Cubit;
- **один способ вместо двух** — меньше решений на каждую надобность.

Отдельное состояние экрана при этом не обязано жить в общем блоке:
*завелась бы в `LibraryState` запись на каждую игру ради одной надобности
одного экрана?* Если да — это свой блок экрана, а не поле в общем.

Cubit в приложении не осталось: двое, заведённых по прежнему правилу,
стали блоками. Первый — пример того, когда своё состояние экрана
оправданно; второй — того, когда оно оказалось ошибкой и переехало на
уровень приложения.

- `RestorePreviewBloc` (бывший `SaveFreshnessCubit`) — куда лягут файлы
  снимка и не новее ли здешние сохранения его самого. Нужно одному
  диалогу восстановления и ровно пока он открыт. Исходов у ответа три, и
  меньше нельзя: «не знаем», «сохранений не было» и «менялись тогда-то».
  Первые два путать нельзя — на неудавшемся чтении диалог заявлял, что
  сейвы никогда не менялись, то есть утверждал то, чего не знал, ровно
  там, где человек решает, затирать ли прогресс;
- `DownloadHistoryBloc` — минута скоростей всех загрузок, по задаче.
  **Один на приложение**, а не на экран: на историю задачи смотрят
  карточка на странице загрузок и страница игры (подложка под заголовком и
  показания у клавиш), а они живут в `IndexedStack` разом. Прежде блок
  заводил виджет `DownloadHistoryScope` вокруг каждого места показа — у
  задачи было две истории, умиравшие вместе с виджетом, а выборку
  добавляли, только когда что-то сдвинулось, и у замершей загрузки график
  стоял. Теперь блок кормится снимками задач из блока загрузок
  (`downloads.stream.map(tasks).distinct()`), выборка — на каждом снимке,
  часы подменяемые, а график и показания выбирают историю по
  `task.id`. Пик и скорость диска — геттеры `DownloadSpeedHistory`: их
  показывают рядом с графиком, и считаться они обязаны от той же истории.

Лежат они в `lib/bloc`, рядом с `notice.dart`, а не подле своих экранов:
такой блок пишет в журнал по-русски, а `lib/ui` для русских литералов
закрыт. Правило это поймало само — страж локализации уронил прогон на
первой же попытке положить его в `lib/ui`.

**Игры и их сохранения — два блока, а не один.** Половина
`LibraryState` была про снимки, и любое движение по ним перестраивало сетку
обложек: страница библиотеки подписана на своё состояние целиком. Лежат они
теперь и на диске врозь — `library.json` и `snapshots.json`, — так что
снятый снимок не переписывает список игр, а испорченный файл уносит одно, а
не оба. Снимки, записанные до 0.33, читаются из библиотечного файла один
раз, при первой загрузке (`saves_storage_test.dart`).

**Зависимость между ними строго в одну сторону.** `SavesBloc` знает
библиотеку — ему нужны игры и их профили; библиотека о нём не знает вовсе.
Что случилось с игрой, она публикует потоками (`gameExits`, `gameRemovals`),
а подписывается на них уже `SavesBloc`. Единственное место, где ждать
приходится библиотеке, — снимок перед запуском: для него у неё есть
`beforeLaunch`, который ставит `SavesBloc`. Правку игры он считает у себя и
пользуется ею сразу, а `SaveRulesAdded` шлёт вдогонку: событие ничего не
возвращает, и ждать чужого состояния значило бы вставить паузу в середину
каждой операции.

**Правка игры — намерение, а не снимок.** Событий вида «вот вся игра»
нет: `GameStatusChanged`, `GameExecutableSet`, `SaveRuleRemoved` и
остальные в `library_event.dart` называют, что меняется, а блок применяет
это к игре, какая она в состоянии **сейчас** (`_edit` в
`library_edits.dart`). Прежний `GameUpdated(game)` нёс игру, захваченную до
ожидания — системного диалога, ответа Steam, — и затирал всё, что пришло
за это время: оценку, кадры, наигранное время. Список спасаемых полей
отставал от модели при каждом новом поле. Новое поле игры, которое правят
снаружи, — это новое событие, а не поле в чужом снимке.

У настроек корень тот же, а лекарство другое: полей там десятки, и
событие на каждое было бы перечнем без смысла. Поэтому записать настройки
можно одним способом — `SettingsPatched(patch)`, функцией от их **текущего**
значения. Прежний `SettingsChanged` нёс настройки целиком, и два быстрых
переключения подряд давали второй снимок со старым первым полем:
включённый автозапуск тут же выключался в системе обратно.

**Сама игра — не двадцать семь полей, а пятнадцать, и четыре из них —
значения.** То, что приходит и правится вместе, лежит одним значением:
`details` (обложка, кадры, описание, оценка, `appid` и маркер поиска в
Steam), `saveDiscovery` (что предложила база путей), `download` (источник,
id задачи, infohash) и `play` (наигранное время и последний запуск).
Правка одной части — `game.copyWith(download: game.download.copyWith(…))` —
другую не задевает уже по устройству, а не потому, что так никто не пишет.
Прежде `copyWith` на шестьдесят строк правил всё одним вызовом.
Рядом с игрой остались `lastError` и `sizeBytes`: ошибкой кончается не
одна загрузка, а размер — свойство установленной игры.

**На диске запись осталась плоской**, с прежними ключами: каждая часть
читает свои из общей карты и туда же пишет (`...details.toJson()`).
`library.json` лежит у людей на дисках, и разбор модели его касаться не
должен. Держит это `model_roundtrip_test.dart` — и то, что записанное
читается обратно, и то, что вложенных объектов в записи нет.

Обработчиков у обоих на несколько файлов. У библиотеки в самом
`library_bloc.dart` остались её устройство и запуск игры, в
`library_edits.dart` — правка игры (`_edit`), в `library_drops.dart` —
брошенное в окно, в `library_metadata.dart` — цепочка «имя раздачи → название → `appid` → пути
сохранений». У сохранений в `saves_snapshots.dart` снимки, в
`saves_hints.dart` подсказки после выхода из игры, в `saves_bulk.dart`
перенос всей библиотеки. Разложены они расширениями
(`extension _SavesSnapshots on SavesBloc`). Плата за это одна и видна в
коде: статику класса расширение обязано звать по имени, то есть
`SavesBloc.snapshotKey(...)`, а не просто `snapshotKey(...)`.

У менеджера сохранений так было и перестало: `RestoreTransaction`,
`EvsavePackage`, `SaveCollector` и `RuleMatcher` — обычные классы со
своими файлами. Расширение удобно, пока части делят состояние целиком; у
этих общего — переводы да предел размера, и передать их параметром
дешевле, чем держать четыре куска одного класса.

**Настройки разобраны на части тем же способом, что и игра.** Из
девятнадцати полей `AppSettings` осталось девять, и три из них — значения:
`appearance` (схема, язык, масштабы, украшения), `startup` (автозапуск,
окно, проверка обновлений) и `saves` (папка синхронизации, автоснимки).
Правят часть через `withAppearance` / `withStartup` / `withSaves`, а
карточка настроек, у которой часть одна, заводит `update` сразу над ней.
Выигрыш не только в `copyWith`: сетка библиотеки выбирает из настроек
один облик (`select` по `appearance`) и больше не перестраивается от
смены папки игр или прокси. Запись на диске плоская, ключи прежние, и это
держит тот же `model_roundtrip_test.dart`.

Событийная модель здесь не церемония: **внешние источники подают события
наравне с нажатиями пользователя**. Лаунчер сообщает о завершении процесса
через `GameExited`, движок загрузок — через `EngineTasksChanged`,
`EngineStatusChanged`, `EngineStatsChanged`, каталог путей — через
`SavePathsProgressChanged`.

Асинхронные операции не пробрасывают исключения в виджеты:

- ключи выполняющихся операций лежат в `state.busy` (`state.isBusy(...)`) —
  собственный `bool _busy` в экранах не нужен;
- результат кладётся в одноразовый `Notice`, а SnackBar'ом его показывает
  только `AppShell` — по слушателю на блок с сообщениями. Два других
  `BlocListener` (`FilesSection`, `SnapshotsSection`) сообщений не
  показывают: они открывают диалог, о котором попросил блок, — выбор
  исполняемого файла, разбор чужого пакета. У `Notice` есть счётчик `seq`: без него
  два одинаковых сообщения подряд считались бы одним состоянием.

Событие ничего не возвращает — отсюда пара мест, выглядящих странно:
`AddGameBloc` сам генерирует id и передаёт его в `GameAdded`, а перед стартом
загрузки дожидается появления игры в состоянии, иначе два блока разошлись бы в
порядке обработки.

`flutter_bloc` построен на `provider`, поэтому оба используются по назначению:
блоки раздаёт `BlocProvider`, сервисы без состояния (`GamepadService`,
`NotificationService`) — обычный `Provider`.

Порядок в `main.dart` важен: настройки читаются до создания остальных блоков
(они нужны им в конструкторе), окно ставится до показа, значок в трее ставится
всегда. Сами блоки и службы собирает `AppServices.bootstrap`
(`lib/app_services.dart`) — там свой порядок и своё объяснение: библиотека,
затем сохранения (они на неё подписаны), затем загрузки, а гаснет всё в
обратном порядке. В `main` остаётся то, что делается один раз и до всего. Язык блоки получают функцией `L Function()` — `BuildContext` у них нет,
а язык может смениться на ходу; по умолчанию `LRu()`.

**Первым шагом `main` берётся замок экземпляра** (`SingleInstance`,
`lib/services/system/single_instance.dart`) — раньше журнала и всего
остального. Два процесса над одними файлами — это два движка над одними
раздачами и уборка одного, стирающая снимки другого: `SnapshotStore.guard`
живёт в памяти одного процесса. Замок — `RandomAccessFile.lock` на
`evaporate.lock` (снимает система, когда процесс гибнет); второй экземпляр
через петлевой сокет, порт которого лежит в `evaporate.port`, просит первый
показать окно и выходит до `runApp` — окно показывается после первого
кадра, поэтому не мелькает. Linux-раннер по-прежнему `NON_UNIQUE`:
единственность держит замок, одинаково на всех трёх системах. Тестируется
вторым процессом (`test/support/single_instance_holder.dart`): на macOS и
Linux замок принадлежит процессу, и захват из того же проходит.

## Запись на диск

`AppPaths` (`lib/core/app_paths.dart`) держит все каталоги: данные приложения —
в системной папке поддержки, сами игры по умолчанию — в домашней, потому что
они большие и их обычно уносят на отдельный диск. В тестах каталоги задаются
напрямую через `AppPaths.custom`, без системных вызовов.

Пишет всё `JsonStore` — **не `File.writeAsString`**, и на то три причины,
каждая проверена:

- запись атомарна (временный файл и переименование): падение посреди записи
  не должно убивать библиотеку;
- записи выстроены в очередь: два одновременных `write` работали бы с одним
  временным файлом, и второй падал бы на переименовании уже переименованного;
- `private` ставит права **на пустом временном файле, до содержимого** — в
  настройках лежит пароль прокси открытым текстом, и он не должен ни мгновения
  лежать читаемым для всех; не сменились права — запись отказывает, а не
  ложится открытой. На Windows это ничего не меняет.

`pretty: false` включают там, где файл читает только приложение (кэш базы
путей — десятки тысяч записей, отступы прибавляют около трети).

## Окно, трей и завершение

Половина записей отложена — библиотека ложится через 400 мс после правки,
положение окна через 500, — а закрытие окна и «Выход» в трее обрывают процесс
мгновенно. Отсюда `AppShutdown` (`lib/services/system/app_shutdown.dart`):
через него проходят **оба** пути выхода, и трею он передаётся как `onQuit` —
своими силами трей умеет только убить окно вместе с процессом, мимо
отложенных записей. Терялось при этом ровно то, что человек только что
сделал: наигранное время сеанса, добавленная игра, подвинутое окно.

Устройство завершения — из того же соображения «пользователь уже нажал
„Закрыть“»: шаги идут по очереди и независимо, сбой одного не отменяет
остальные, у каждого свой предел и у всех вместе общий бюджет (зависший
движок не имеет права оставить окно на экране навсегда). Повторный вызов
получает **тот же** проход (`_running ??= _run()`), а не пустой ответ:
закрытие окна и «Выход» могут прийти одно за другим, и второй `quit()`
прежде заканчивал процесс посреди первого прохода. Окно `quit()` прячет
первым делом — иначе оно секундами оставалось на экране и нажималось.

Окно живёт в `WindowState` + `ManagedWindowController`: обёртка нужна затем,
чтобы логику восстановления можно было проверить тестами — настоящее окно в
тестовой среде не создать. Запомненные числа перед применением проходят
`sanitized()`: монитор могли отключить или сменить разрешение, и окно по
старым числам окажется за краем экрана — человек решит, что приложение не
запустилось. `NaN` отсеивается **до** `clamp`, иначе испорченная ширина
превратилась бы в окно на двадцать тысяч точек. Перетаскивание сыплет
событиями десятками в секунду, поэтому запись отложена, но при выходе её
дописывают немедленно (`flush`).

`WindowStartMode` — один выбор из трёх (как оставили / развёрнутым / свёрнутым
в трей), а не набор галочек: «свёрнуто» и «развёрнуто» взаимоисключающи.
Ради третьего варианта значок в трее и ставится **всегда**: приложение,
стартовавшее с системой и не показавшее окна, иначе было бы ничем не открыть.

Сам трей — `tray_manager` 0.7, то есть `TrayIcon` из `nativeapi`: прежний
API там в `legacy.dart` и помечен устаревшим, а анализатор проекта такого не
пропускает. `AppTray` держит только смысл — меню данными (`menuEntries`) и
выбор пункта именем (`onMenuSelected`), — а системную часть отдаёт
`TrayHost`. Настоящий (`NativeTrayHost`) импортирует один `main`, и в
покрытии он назван среди непроверяемого, как системные уведомления; тесты
ставят подделку. Не вставший значок пишется в журнал, окно показывается, а
`--smoke` на Windows и macOS требует, чтобы значок встал. На Linux не
требует: значок там — StatusNotifierItem, и без панели, которая такие
принимает (под `xvfb` в CI её нет, в GNOME — без расширения), он не
показывается, не будучи поломкой.

## Перенос сохранений — суть приложения

Почему всё устроено именно так и какой ошибкой оплачено каждое правило —
[docs/architecture/saves.md](docs/architecture/saves.md). Правила:

- В профиле игры хранится **шаблон пути**, а не абсолютный путь —
  `{APPSUPPORT}/MyGame/Saves` (`lib/core/save_path_template.dart`,
  `expand`/`collapse`). `{DOCUMENTS}` и `{SAVEDGAMES}` называет система
  (`SystemFolders`), прочие корни — догадка. Правило шире папки сохранений
  не разворачивается (`SavePathTemplate.isTooBroad`).
- `.evsave` — zip из `manifest.json` и `data/<ruleId>/...`, и читают его
  чужие сборки на других устройствах: несовместимая правка формата —
  сначала issue. Читаемые версии — множество
  `SaveSnapshot.readableFormats`, старые из него не убирают. Правила
  сопоставляются по id, затем по метке; распаковка проверяет zip-slip.
  Момент снятия — UTC со смещением (`SaveSnapshot.writeMoment`),
  нечитаемая дата — эпоха; время файлов — в манифесте (`modified`).
- Локально снимки лежат в хранилище по содержимому (`SnapshotStore`), и
  восстановление раскладывает файлы прямо оттуда. Раскладка одна
  (`RestoreSource` различает только источник байтов) — второй не заводить.
- Уборка хранилища: всё, что кладёт содержимое, — под
  `SnapshotStore.guard`, а `collect` при незакрытой работе не начинается;
  не целиком прочитанный `snapshots.json` запрещает уборку до конца
  сеанса (`_unread` в `SavesBloc`); убранное уходит в корзину
  `blobs-trash` на две недели.
- Хеш и сжатие файлов от мегабайта, сборка и разбор `.evsave` — в изоляте
  через `Offload`; работа для изолята — статика из строк (`EvsaveJobs`),
  а не замыкание, тащащее `this`.
- Восстановление сперва снимает резервную копию; массовая загрузка
  пропускает игры, где это устройство ушло вперёд (допуск две минуты).
  Перенос всей библиотеки — `BulkTransfer`, а не блок.
- Откуда пути: `LudusaviCatalog` (по требованию, разбор в изоляте, в
  репозиторий не входит), `SaveActivityWatch` (результат —
  **предложение человеку, а не запись молча**), `SavePathFinder`.

## Загрузки

Почему всё устроено именно так —
[docs/architecture/downloads.md](docs/architecture/downloads.md). Правила:

- `DownloadEngine` — контракт, `DtorrentEngine` — единственная
  реализация. Контракт описывает всё, что движку поручают:
  `DownloadsBloc` получает движок параметром и тестируется через
  `FakeDownloadEngine` (`test/support/`).
- `dtorrent_task_v2` — **форк** (`Hecatoncheir/dtorrent_task_v2`, коммит
  закреплён в `pubspec.yaml`). Правки библиотеки идут в форк, не сюда.
- Прокси — перехват создания `HttpClient` (`ProxyHttpOverrides`, ставится
  в `main`). Каталоги Steam и путей сохранений решают сами по флагу
  `useForSteam` и берут `directHttpClient()`; обновление ходит через
  прокси (`updateHttpClient`). **Недоступный прокси отказывает, а не
  пропускает напрямую** (`ProxyUnreachableException`); куда уходит HTTP —
  `ProxyHttpOverrides.routing`. При прокси у задачи нет `udp://` и
  `ws(s)://` трекеров (`announcesFor`), при SOCKS5 форк не поднимает
  DHT, LSD и uTP.
- Пределы скорости — два общих `BandwidthLimiter` на весь движок;
  `addScheduleWindow` библиотеки не звать (`dtorrent_engine_test`).
- `DownloadLink.fromJson` читает старый ключ `downloadGid` — не удалять,
  пока такие библиотеки лежат у людей.
- `.torrent` читаем и пишем сами (`TorrentFile`): infohash из
  `dtorrent_task_v2` неверен, и `TorrentSource.fromBytes` считает его по
  вырезанным байтам info-словаря. Magnet собирается в настоящий файл в
  `torrentsDir/<infohash>.torrent`; где искать файл раздачи, знает
  `TorrentExport`.

## Свои игры в библиотеке Steam

`SteamShortcuts` (`lib/services/launch/steam_shortcuts.dart`) заводит игру в
Steam сторонним ярлыком. API у Steam для этого нет — список лежит у него в
`userdata/<id>/config/shortcuts.vdf`, **двоичным** VDF, и мы его переписываем.
Разбирает и собирает `BinaryVdf`; текстовый `Vdf` здесь ни при чём, это другой
формат, а не другой синтаксис.

**Три правила защищают чужое добро, а не наше удобство.** `BinaryVdf.decode`
бросает на всём незнакомом, и отказ проходит наружу: переписать список,
разобрав его наполовину, значит стереть ярлыки, которые человек заводил сам.
Перед записью прежний файл ложится копией рядом, и копий две: `.bak` — до
последней записи, `.orig` — до самой первой, её не переписывают (одна копия
со второй правки хранила уже наш список). А при запущенном Steam не
пишем вовсе: Steam держит список в памяти и выкладывает его при выходе, так
что наша запись исчезла бы молча, — отказ приходит сообщением.

Порядок ключей значим и сохраняется: разбор с обратной сборкой дают файл байт
в байт, и `binary_vdf_test.dart` держит это на раскладке, снятой с настоящего
файла Steam. Оттуда же две подробности, которых по документации не узнать:
`Exe` Steam берёт в кавычки, а `StartDir` нет, и у последнего есть
завершающий разделитель.

**`appid` мы назначаем сами, и это выяснено опытом.** Steam назначает его
только когда сам заводит ярлык, а написанный в файле принимает как есть; его
собственное значение не сошлось ни с одной из общепринятых формул, включая
`crc32(Exe + AppName)`, которой пользуются сторонние инструменты. Поэтому
число берём от **нашего id игры**, а не от пути: переставит человек игру на
другой диск — число то же, и положенные в `grid` обложки не осиротеют.
Старший бит взведён: им Steam метит сторонние ярлыки.

**Витрина — четыре картинки, а не одна**, и лежат они в
`userdata/<id>/config/grid`, где имя и решает роль: `<appid>p.jpg` —
вертикальная для сетки библиотеки, `<appid>.jpg` — горизонтальная плашка для
полок и списков, `<appid>_hero.jpg` — задник страницы игры, `<appid>_logo.png`
— название поверх него. Положив одну, получаешь игру, которая в сетке как все,
а на своей странице пустая.

У игры с известным `appid` все четыре берутся с CDN Steam (`SteamCatalog`:
`portraitUrl`, `capsuleUrl`, `heroUrl`, `logoUrl`) — их рисовали для неё самой.
Четыре запроса идут разом, и это не то же, что залп по каталогу из
`SteamLookupRequested`: там сорок игр ломились в опросную точку магазина, здесь
одна игра берёт четыре картинки с раздающей сети по прямому нажатию человека, а
последовательные ожидания сложились бы в минуту на одной зависшей.

Сохранённая обложка закрывает ту створку, что осталась пустой, — игра могла
прийти не из Steam вовсе. Ложится она по пропорциям, прочитанным из заголовка
картинки: каталог сначала просит `library_600x900`, а если её не рисовали,
берёт горизонтальную `header`, и горизонтальная под именем вертикальной
растянулась бы на 600×900. Неудача с витриной ярлыка не отменяет: игра без
обложки — это игра без обложки.

## Поиск установленных игр

`LibraryScanner` отличает игру от **собрания игр** по числу разных подпапок с
исполняемыми файлами: у игры такая одна (даже если это `Binaries/Win64` у
Unreal), у собрания их столько же, сколько игр. Спорный случай — собрание из
одной игры — выдаёт отсутствие файлов рядом: у игры в корне всегда
что-нибудь лежит. Без этого выбор диска целиком давал одну «игру» с именем
контейнера, накрывавшую всю коллекцию.

`SteamInstall` читает `libraryfolders.vdf` и `appmanifest_*.acf` с диска
(`Vdf` — свой разборщик, без зависимости). Оттуда берутся точные `appid` и
названия; по `appid` дальше ищутся пути сохранений, и это единственный
способ не подставить сейвы другой игры с похожим именем. Каталога содержимого
в приложении по-прежнему нет: читаются файлы на диске самого игрока.

`ScanSession` держит ход обхода и его отмену через **поколения**: заход,
который отменили, не дописывает найденное в список следующего. Поиск
стартует до выбора папки — пока человек ищет её в системном окне, известные
места (`GameRoots`) уже осматриваются. Остановка не выбрасывает найденное:
«хватит искать» и «забудь найденное» — разные вещи.

`~/Documents`, `~/Desktop` и `~/Downloads` в `GameRoots` намеренно не входят:
на macOS обход каждой вызывает системный запрос прав, а поиск теперь
начинается сам, без отдельного нажатия.

## Название, обложка и appid

Цепочка, которой не видно по одному файлу: **имя раздачи → название → `appid` →
пути сохранений**. `ReleaseName` (`lib/services/metadata/`) чистит
`The.Witcher.3.Wild.Hunt.GOTY.MULTi15-ElAmigos` от версий, меток релиз-групп и
языков; `SteamCatalog` по очищенному названию находит `appid`, описание и
обложку; по найденному `appid` дальше ищутся пути сохранений — и это
единственный способ не подставить сейвы другой игры с похожим названием.
Держит цепочку `automatic_metadata_test.dart`.

**Сеть, файлы и состояние разведены по трём местам.** В Steam ходит
`GameMetadataFetcher` (`lib/services/metadata/`) и отдаёт всё за один
заход — `appid`, описание, обложку байтами, кадры и оценку; файлы кладёт
и убирает `CoverCache` оттуда же; блоку остаётся отметить попытку,
убедиться, что игра всё ещё та самая, и записать найденное. Прежде это
лежало в одном обработчике на девяносто строк со сложностью 29, и
проверить из него можно было лишь то, что переживёт настоящий HTTP.

У `CoverCache` своё правило, ради которого он и отдельный: **трогаем
только свой кэш**. Обложку, выбранную человеком, он мог положить куда
угодно — она не наша, и ни заменять, ни удалять её нельзя.

Три решения в `LibraryBloc`, каждое оплачено ошибкой:

- `SteamLookupRequested` и `SavePathsLookupRequested` обрабатываются **по
  одному за раз** (`asyncExpand`), а не параллельно, как Bloc умеет по
  умолчанию: загрузка библиотеки ставит поиск каждой игре сразу, и сорок игр
  давали сорок одновременных соединений со Steam. Steam на залп отвечает
  отказом, а маркер «уже пробовали» к тому времени записан — игры оставались
  без обложек навсегда. Цена — очередь: ручной поиск во время разбора большой
  библиотеки дождётся своей очереди.
- **Кнопок обновления две, и это не дублирование.** «Поискать для всех»
  (`MetadataRetryRequested`) идёт только за нехваткой, «Обновить всё»
  (`MetadataRefreshRequested`) — за всем и по каждой игре. Приложение
  прирастает точками данных: сперва добавилась оценка, потом кадры из игры,
  — а у сложившейся библиотеки нехватки нет, и первая кнопка честно
  отвечает «метаданные есть у всех». Прежде под каждую новую точку правили
  отбор «чего не хватает»; вторая кнопка избавляет от этого навсегда.
- Маркер `steamLookupAttempted` пишется **до сети**, чтобы аварийный выход не
  вызывал повтор; отказывает в поиске только он. Наличия `appid` для отказа
  мало: он мог прийти из манифеста Steam на диске, и обложки у игры ещё нет.
- Найденным названием карточку **не переписывают**: имя в библиотеке
  пользователь мог задать сам. А если `appid` уже известен, спрашивают прямо
  по нему: поиск по названию тут не лишний, а вредный — он способен ответить
  другой игрой.

**Обзоры — четвёртая точка, и подпись к ним чужая.** В `appdetails` их нет
вовсе: итог считает `appreviews/<appid>`, и просить его надо с
`language=all`, `purchase_type=all` и `num_per_page=0` — иначе Steam
посчитает обзоры на одном языке и только от купивших у него же, а к итогу
приложит два десятка полных текстов. Запрос идёт в той же очереди поиска
метаданных (`SteamLookupRequested`), но со своим `try`: промолчи Steam об
обзорах — игра всё равно получит обложку, описание и пути сохранений.

Подпись («Очень положительные») хранится **как её написал Steam**, а не
собирается из своей таблицы: ступеней десять, проверены на живых ответах не
все, и придуманное слово сказало бы о вкусах игроков то, чего мы не знаем.
Ступень (`review_score`, 0–9) при этом хранится и используется ровно на одно
— на цвет: у Steam граница между «смешанными» и «в основном положительными»
зависит ещё и от числа обзоров, и своя граница по проценту красила бы
вопреки подписи. Показываются доля положительных, оба счётчика и, если она
есть, оценка Metacritic из тех же `appdetails`.

## Перетаскивание в окно

`DropImport` (`lib/services/launch/drop_import.dart`) решает, чем оказалось
сброшенное: папка — установленная игра, `.torrent` — игра в очереди загрузки,
остальное помечается неподходящим и не проглатывается молча. Решение живёт
отдельно от виджета и проверяется на настоящих файлах.

Приёмник один на оба экрана — `GameDropTarget` (`lib/ui/widgets/`): бросают
туда, где сейчас смотрят, и библиотеке с загрузками расходиться в этом
незачем. **Молчать при этом обязан невидимый раздел.** Разделы живут в
`IndexedStack` все разом — невидимый не выброшен, а только не нарисован, —
и оба приёмника ловили бы один и тот же сброс, заводя из одного файла две
игры. Видимый отличается по `TickerMode`: `FadeIndexedStack` включает его
ровно текущему разделу, и тот же признак уже слушают украшения.

**Magnet-ссылку сюда не притащить, и это не недоделка.** `desktop_drop` читает
на macOS только file-URL, на Windows — только `CF_HDROP`; ссылка из браузера
приходит как `public.url` / `CFSTR_INETURL` и до приложения не доезжает.
Пакет, который это умеет (`super_drag_and_drop`), тянет Rust в сборку — от
него отказались сознательно. Magnet вставляют в «Добавить игру».

## Ввод: клавиатура и геймпад — один словарь

`NavAction` (`lib/input/nav_action.dart`) — единый набор действий; и клавиши, и
кнопки контроллера сводятся к нему, дальше по приложению идёт только `NavAction`.
`InputScope` в оболочке добавляет недостающие `Shortcuts`/`Actions` и мостит
поток геймпада. `DirectionalFocusIntent` перехвачен намеренно: штатный
обработчик не умеет стартовать с пустого фокуса. Раскладка живёт в настройках,
применяет её `GamepadService`.

**Что делает главная клавиша игры, решает одно место** — `primaryActionFor`
в `lib/ui/library/primary_action.dart`. Мест, где эта клавиша есть, четыре:
кнопка X на геймпаде, крупный кадр библиотеки, подпись у его клавиши и
карточка на странице игры; `switch` по состоянию игры стоял в каждом, причём
в оболочке и в библиотеке — побайтово один и тот же. Доступность
(`canDoPrimaryAction`) вынесена отдельно от действия нарочно: у погашенной
клавиши остаётся своя подпись — «Играть» у игры без выбранного
исполняемого файла, — и, слив «нечего делать» с действием, мы получили бы
клавишу без слова на ней.

## Оформление

Почему облик устроен именно так, с числами и историей —
[docs/architecture/design.md](docs/architecture/design.md). Интерфейс
сейчас обновляется по `docs/redesign-plan.md`, и фазы плана правят этот
раздел и тот документ. Правила:

- Две схемы — два самостоятельных облика (ночная «Арклайт», дневная
  «Картридж»), и **расходятся они данными, а не ветвлениями**: `isDark` в
  виджетах нет, различия лежат в `ThemeExtension` с двумя экземплярами,
  `arclight` и `cartridge` (`HardwareSurfaceTheme`, `EffectsPalette`,
  `GlassSurfaceTheme`).
- Облик задаёт тема, а не виджет (`theme_structure_test`), и виджеты
  импортируют бочку `lib/ui/theme.dart`: цвета — `context.colors`; текст —
  ролями `context.text.*` из `typography.dart`, по месту роль правят
  только цветом, а иной облик — новая роль; отступы — `EvaporateSpacing`,
  значки — `EvaporateIconSize`, радиусы — `radiusPanel`, `radiusControl`,
  `radiusChip` (и `radiusSelection`), моторика — `context.motion`
  (уважает `disableAnimations`), размеры раскладки — `EvaporateLayout`.
- `primary` — для текста и значков, `primaryFill` — для заливок под
  `onPrimary`; так же `accent`/`accentFill` и `danger`/`dangerFill`.
  Контраст по WCAG меряет `test/ui/theme/theme_test.dart`.
- Шрифты: Unbounded (заголовки, заглавными с положительным разрядом),
  Golos Text, JetBrains Mono (пути и показания).
- Картинки расшифровываются под размер показа (`decodeWidth`).
- Украшения — набор `LibraryEffect` в `Appearance`, показываются
  наборами `EffectPreset`; значения по умолчанию сторожит
  `effect_settings_test.dart`. Кадры всем гонят одни часы
  (`DecorationClock`), и когда стоять, решает одно правило —
  `decorationMayRun`.
- Диктору: подпись плитки — внутри неё под `MergeSemantics`
  (`test/ui/library/semantics_test.dart`); заглавные подписи уходят
  обычным словом.

Правило уведомлений: **SnackBar — для того, что пользователь только что нажал
сам; системное уведомление — для того, что закончилось в фоне** (загрузка
завершена, загрузка сорвалась, автоснимок после выхода из игры не удался). Об
ошибке загрузки уведомляем один раз — на переходе в состояние, а не на каждом
опросе движка.

## Журнал

`AppLog` (`lib/services/system/app_log.dart`) заводится в `main` раньше всего
остального и пишет в `<dataDir>/evaporate.log` с поворотом одного поколения.
Туда уходит каждый `Notice` с `isError`, а также места, которые гасят ошибку
молча: уборка хранилища снимков, ротация, обход папок в поисках следов игры,
выгрузка в папку синхронизации. Наружу журнал не уходит — его показывают в
настройках (`LogCard`), а отправлять решает человек.

**Имя каждого события блока пишется и в выпускной сборке**
(`LoggingBlocObserver.onEvent`) — это и есть «журнал причин», ради которого
приложение держится Bloc; прежде он был только в отладке, то есть у человека
его не было. Только имя, не содержимое. Частые события — снимки движка
каждую секунду, стрелки по сетке, буквы поиска — помечены `FrequentEvent`
(`lib/bloc/frequent_event.dart`) и в журнал не идут: новое такое событие
помечают так же, иначе журнал утонет. Туда же сведено то, что падает мимо
блоков (`AppLog.captureUnhandled`: ошибки Flutter и необработанные
асинхронные), и сбои шагов завершения.

Запись — настоящий файловый ввод-вывод, поэтому в `testWidgets` и она, и
чтение идут через `tester.runAsync`; опрос состояния после этого — **снаружи**
`runAsync`, потому что кадры внутри него в цикле не идут.

## Тесты

**`test/` лежит зеркалом `lib/`** — `test/core/`, `test/models/`,
`test/input/`, `test/bloc/`, `test/services/<область>/`,
`test/ui/<раздел>/`, плюс `test/guards/` (правила кода), `test/support/`
(общее) и `test/tool/` (то, что проверяет сам репозиторий: `ci.yml`,
`CHANGELOG.md`, отчёт о покрытии). Прежде все сто тридцать файлов лежали
одной папкой, и найти тест к файлу было делом перебора.

**Кладут по тому, о чём тест, а не по тому, что он импортирует.**
Разложить по импортам не выходит: половина файлов — виджет-тесты, которые
заодно трогают модели, блоки и сервисы, и механика уносит их в
`test/models/`. Тест, положенный не туда, хуже плоского списка — его
будут искать там, где его нет. Поэтому `drop_import_test` лежит у
виджетов (пять его проверок идут через настоящее окно), а
`bulk_report_test` — рядом с `bulk_transfer_test` в сервисах, хотя
поднимает блоки.

Один виджет в окружении приложения — тема, язык и `Scaffold` — собирает
`hostWidget` (`test/support/host_widget.dart`). Параметров у него два,
схема и язык, и расти они не должны: обвязка, отличающаяся по делу
(свой `MediaQuery`, `builder` рамки окна), пишется на месте — флаг на
каждый такой случай прятал бы, ради чего тест окружение и завёл.

`test/support/test_app.dart` собирает всё приложение с подменённым потоком
геймпада. Две ловушки записаны там же в комментариях: `TestHarness` **обязан**
создаваться внутри `testWidgets` (Bloc запоминает зону подписки, и блок из
`setUp` доставлял бы события мимо фейкового времени), а временная папка,
наоборот, готовится снаружи — настоящий файловый I/O внутри `testWidgets` не
завершается никогда. По той же причине `saveRoots: () => const []`: обход
настоящих «Документов» не закончится.

**«Ничего не произошло» проверяют барьером, а не паузой.** `HandlerTracker`
(`test/support/bloc_idle.dart`, ставится `installHandlerTracker()` в
`setUp`) считает принятые и отработанные события всех блоков, и
`handlers.settle()` ждёт, пока в работе не останется ни одного. Пауза в
50 мс на медленной машине проходила вхолостую: обработчик просто не
успевал, и «движку ничего не поручили» подтверждалось само собой.

Правка, меняющая поведение, идёт с тестом; правка, исправляющая ошибку, — с
тестом, который без неё падает.

## Стражи: правила, которые держит прогон

Правило, которое помнят, а не проверяют, не держится. Поэтому у правил
кода есть тесты-стражи в `test/guards/`, а их общее — в
`test/support/guards.dart`:

- `widget_structure_test` — **один файл — один публичный виджет**, и ни
  методов и функций, возвращающих виджеты (кроме `build`): метод-виджет
  лишён своего `Element` — без границы перестроения, без `const`,
  невидимый в инспекторе. Приватный виджет (`class _Foo extends
  StatelessWidget`) законен в файле своего единственного потребителя, пока
  он не длиннее 40 строк и без своего `State` с ресурсами; нужен второму,
  вырос или завёл `dispose` — в свой файл под публичным именем
  (`docs/decisions/0009`). Следующая ступень — то, чем правило обходят:
  замыкание-строитель в `build` длиннее 25 строк (`buildClosures`) и виджет
  больше чем с семью параметрами (`wideWidgets`), оба храповиком с числом.
  И общая папка `lib/ui/widgets` держит только нужное хотя бы двум местам
  (`lonelyShared`); места считаются за папкой, так что часть
  переиспользуемого виджета законна, а нужное одному экрану живёт у него.
- `theme_structure_test` — вне файлов темы нет `isDark`, `fontSize:`,
  `Duration(milliseconds:`, `BorderRadius.circular(<число>)`, чисел
  раскладки (поле 28, ширины 1340 и 220, диалоги 460 и 560), кривых `Curves.*` (у переходов их три токена — `EvaporateMotion.ease`, `enter`, `exit`), прозрачности числом —
  она берётся ступенью `EvaporateAlpha`, — промежутков, полей и
  размеров значков числом, правки роли текста не цветом и `TextStyle` по
  месту с чем-то кроме цвета (`test/support/text_roles.dart`): облик
  задаёт тема, а не виджет. Тема — в три яруса: примитивы (сырые числа,
  приватно в файлах схем) → семантические токены (`context.colors`,
  `context.motion`, типографика) → тема компонента (`ThemeExtension` рядом
  с виджетом, два экземпляра на две схемы, а не наследники). Там же
  проверяется, что набор расширений у схем один и переживает смену схемы.
- `layering_test` — блоки, сервисы, модели и ядро не импортируют `lib/ui`;
  сервисы — блоков; модели и ядро — блоков, сервисов, ввода и пакетов вне
  белого списка чистого Dart (плагин запрещён, даже если не назван).
  Проверка **транзитивная**: запретное, до которого слой дотягивается
  своими импортами, — то же нарушение (так в моделях нашёлся
  `package:gamepads` через раскладку геймпада).
- `complexity_test` — сложность функции не выше 15, длина не больше 60
  строк, вложенность не глубже 3. Списки нарушителей пусты у всех трёх:
  за этим потолком функцию перестают читать целиком, и лечится это ранним
  выходом, таблицей или именованным шагом. Последней ушла `Game.copyWith`
  — не переносом строк, а разбором модели на значения. Замер — `tool/check_complexity.dart`
  (`dart tool/check_complexity.dart` покажет самые тяжёлые); пороги держат
  следом за достигнутым, как покрытие.
  Замер читает **синтаксическое дерево** `package:analyzer`
  (dev-зависимость), а не текст: разбор скобками пропускал конструкторы
  блоков со списком инициализации (у `LibraryBloc` — девяносто пять
  строк), фабрики `fromJson` и `operator ==`. Сложность — по SonarSource:
  `when` у образца стоит единицу, `??` и `?.` не считаются, ветви
  тернарника и замыкания вложены. Язык опередил пакет — страж «разбирает
  каждый файл без ошибок» красный, и `analyzer` поднимают. Почему так —
  `docs/decisions/0006-complexity-on-analyzer.md`.
- `arb_usage_test` — каждый ключ ARB кем-то читается, и именно у
  переводов (`l.`, `_l.`, `L.of(context).`, `…localizations().`), а не
  одноимённым полем: прежде `source` жил за счёт `download.source`.

**У каждого стража есть таблица «ловит / не ловит»** — группа «страж
ловит нарушение» с фрагментами кода. Сломанная регулярка — вечная
зелень: страж, который ничего не находит, выглядит ровно как страж,
которому нечего найти. Детекторы для этого — функции над `SourceFile`
(`test/support/widget_structure.dart`, `layering.dart`), а не выражения,
зашитые в тело теста.

**Устройство блоков сторожит `bloc_lint`** — отдельный шаг CI
(`bloc lint lib` из `bloc_tools`), потому что своего плагина у пакета нет
и анализатор его правил не читает. Набор задан в `analysis_options.yaml`
под ключом `bloc`, и там же записано, почему включено именно это.
Главное правило — `prefer_bloc`: то самое «по умолчанию Bloc», но
поставленное на ворота, а не запомненное. Исключения помечены в коде
`// ignore:` поимённо, каждое со своим объяснением рядом; список их
короткий и расти не должен — это тот же храповик, только чужой.
`avoid_public_bloc_methods` в 0.4.2 не видит членов после первого
`@override`, поэтому у него свой страж — `bloc_members_test`: каждый
публичный метод и геттер блока помечен и объяснён.

**Стражи — храповики.** Каждый несёт список известных нарушителей на
момент введения правила. Пополнять список нельзя: новое нарушение роняет
прогон. Но и исправленное обязано из списка уйти — иначе на его место
незаметно встало бы новое. Там, где в записи стоит число (сколько раз, какая
сложность), выросло — это новое нарушение, уменьшилось — число правят
следом. Уборка идёт по частям, и новых нарушений не появляется.

Линтер держит своё: помимо набора `flutter_lints` — `only_throw_errors`,
`avoid_positional_boolean_parameters`, `prefer_single_quotes` и другие в
`analysis_options.yaml`; в `lib/bloc` и `lib/services` вложенными
настройками включён ещё и `discarded_futures`.

  правкой в `lib/ui` сверяйтесь с ним.

## Что обсуждать до правки

Новый экран, замена зависимости, смена формата `.evsave` — сначала issue.
Формат снимков особенно: его читают чужие сборки на других устройствах.

Прежде чем предлагать слой, блок или зависимость, загляните в
`docs/decisions/`: репозиторий игр, блоки захвата кнопки и окна, `bloc_test`,
`freezed` и DCM уже рассматривали и отклонили — там записано почему и когда
вопрос стоит пересмотреть. Новое решение с причинами ложится туда же
следующим номером.
